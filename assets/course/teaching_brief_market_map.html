03
— POC Methodology · S0–S2

用 Gen-AI 把 PRD features 變成多技術棧 variants

回到 Gantt 圖上那塊被 ochre 淡色標出的區域——S0 到 S2——就是 POC 階段。設計師這三個 sprint 真正做的事不是「畫畫面」，而是把 PRD 裡技術棧無關的功能描述（"使用者可以管理通知"）轉換成特定技術棧內可比較、可選擇的多個 variants。這一節要拆解的就是：怎麼用 AI 工具有效地做這件事。

3.1 同一 feature × 四種技術棧 — same feature, four design languages

3.3 四個常見誤區 — recurring failure modes

POC 階段最容易出錯的，不是 AI 生成本身，是設計師對 AI 輸出的處置方式。下面是課程中反覆看到的四個失敗模式。

# 誤區 症狀 修正
1 沒指定技術棧 AI 給出 web 樣式 + mobile gesture + admin table 拼貼的「四不像」 Prompt 開頭必寫 platform + primary viewport + design system
2 variants 都覺得不錯 陷入「再生一輪試試」的循環，選不出來 生成前先寫好 3 條 selection criteria，再開生成
3 variants 當交付物 直接把 AI variant 丟進 Figma，工程師發現邏輯破洞回頭重做 variants 只是材料；只挑 1 個進 Figma 微調 + spec 補完
4 不寫選擇理由 三週後同樣決策又要再來一次；新成員問「為什麼」沒人答得出 第 5 步是強制 gate；沒 decision log 不能進下一個 feature
POC 階段
的本質
POC 階段的本質是「用 AI 製造可比較的選項，用設計師的判斷收斂」。Gantt 圖上那塊 ochre 區域之所以橫跨 S0–S2 三個 sprint，是因為 Tier A 文件（persona / use case / scenario）必須在前面，否則 Step 02 的「指定技術棧 constraint」沒有素材；Tier B 文件（journey、flow）也要同步成形，因為 variants 要對照流程才有意義。

換句話說：沒有前置的 Tier A + Tier B，AI Variants 就只是隨機產生器。POC 不是「先做個原型試試」——它是「用結構化前置 + AI 變體生成 + 設計師判斷」的三件套。三件少了任何一件，POC 就退化成上市場已經一堆的 prompt-to-UI 把戲。

左欄是不可變的原始素材（PRD、journey、模塊清單⋯⋯），右欄是專責的 agents（Design / Research / Copy / Red Team），中間的 wiki 是兩者的介面。 設計師（PM / UR / UIDes 都算）的新身份是「UX Writer / Curator」——用 CoT 寫作維護中間那層，順便編排右邊那組 agents。

Raw Sources 原始素材 immutable，永遠不改寫。透過 MarkItDown 一次性 ingest 成 markdown。
LLM Wiki 三層：catalog (index.md) · log (log.md) · curated pages · 加上 schema/CoT 規則。
UX Agents 四個專責 worker + 一個 Orchestrator。Orchestrator 就是你——用 CoT 寫作做策展。
03
— INGEST · the rust dashed arrow

MarkItDown 是入場券，不是答案

上圖 INGEST 那條 rust dashed line，是把 raw sources（PRD、Word、PPT、PDF、會議錄音）轉成 markdown 的工具帶。 Microsoft MarkItDown（MIT 授權、87k stars、Python API + CLI + 內建 MCP server）是目前最便宜可靠的選擇——但要當 Lesson 2 的教學素材，要立刻把它的邊界講清楚：它只解了「便宜的那一半」。

MarkItDown 解決的部分

純格式轉換 · commodity infrastructure
  • 把 .pdf / .docx / .pptx / .xlsx 轉成乾淨 markdown
  • 圖片做 OCR + EXIF metadata 抓取
  • 音訊做 speech transcription（會議錄音 → 逐字稿）
  • HTML / CSV / JSON / XML / EPub / YouTube URL 一鍵 ingest
  • 內建 markitdown-mcp server，可直接掛 Claude Desktop / Claude Code
  • Plugin 架構，可寫自訂 converter（之後 Figma 匯出可走這條）

MarkItDown 不解決的部分

設計知識架構 · curator 的核心判斷
  • 不會 summarize（Karpathy LLM Wiki 的核心動作）
  • 不會建 cross-reference（不同文件間的實體對齊）
  • 不會 file / categorize（這份輸出該放 persona/ 還是 decisions/？）
  • 不會生 index.md / log.md
  • 不懂 schema / frontmatter / naming convention
  • 不認識「設計知識」——它不知道 page list 和 user flow 在語意上是不同物件

— 失真風險：MarkItDown 跑得過、但設計知識被掏空的四種情境

convert ≠ understand。下面四種來源是教學上最容易被忽略的陷阱——它們表面都能被 MarkItDown 處理，但設計知識在轉換時被掏空。學員要學的不是修工具，是學會在工具失真的地方插入自己的判斷。

來源類型 MarkItDown 處理後的狀態 設計知識的損失 Curator 必須補的
Figma 匯出 PDF 圖被 OCR 或變 base64 embed 元件結構、tokens、variants 全失 component reference page
流程圖 / wireframe 圖片轉描述性文字（OCR） 空間關係、連線意義消失 手寫 Mermaid 或 frontmatter 補連線語意
會議錄音 逐字稿（含時間戳） 誰主張什麼、誰反駁——需手工 markup decision log + speaker attribution
複雜版面 Word 主結構保留，註解 / 修訂紀錄常掉 side comments、track changes 不見 手動把關鍵 comment 抽到 page bottom
04
— Curation · the expensive half

從 raw markdown 到 LLM Wiki：策展三件事

把 MarkItDown 出來的 raw markdown 變成 agent 讀得懂的 LLM Wiki，curator（也就是設計師）要做三件事。這三件事就是 Lesson 2 的核心 lab——MarkItDown 解的是 Lab 0（前置自學），下面這三件是 Lab 1（課內核心）。

4.1 · SCHEMA
加 frontmatter 規範
— enforce file shape
為每種文件類型（persona、use case、decision、page）定義 YAML frontmatter schema：必填欄位、命名規範、tag 詞彙表。schema 就是架構的 source of truth。
IN · raw.md from MarkItDown
OUT · persona.md with strict frontmatter
4.2 · CROSS-REF
建 backlinks 與 tags
— wire up the web
單一 markdown 是孤島——讀完 persona 不知道哪些 journey 對應、改完 page 不知道哪些 decision 受影響。用 frontmatter 欄位（related:）或內文 [[wiki-link]] 把文件之間的關聯顯式寫出來，agent 才能在文件之間 traverse。
IN · 一份孤立的 markdown
OUT · 接入 cross-ref graph 的節點
4.3 · CATEGORIZE
寫進 index.md / log.md
— file it where agents look
index.md 是分類目錄（agent 用它導航），log.md 是時序記錄（agent 用它追歷史）。每份新文件都要同時 register 進這兩個——這是讓 wiki 不腐爛的最低紀律。
IN · 新增的 wiki page
OUT · index.md + log.md 同步更新
範例 · WORKED EXAMPLE cross-ref 怎麼讓 agent 串起四份文件

場景：有人問 agent「為什麼 notification-prefs 頁面的預設模式是 digest？」 沒有 cross-ref，agent 只能讀到「預設是 digest」這一行死資訊，回答不出為什麼。 有 cross-ref，agent 順著三份文件之間的 frontmatter 關係走完下面這條 trail，就能給出有 persona 支撐的理由。

1.
page/notification-prefs.md 
---
type: page
id: notification-prefs
default_mode: digest
implements: [d-2026-04-default-digest]
serves_personas: [sarah-busy-parent]
---
↓ 順著 implements 跳到對應的 decision
2.
decision/d-2026-04-default-digest.md 
---
type: decision
date: 2026-04-15
status: active
applies_to_personas: [sarah-busy-parent]
overrides: ios-default-immediate
trade_off: digest 損失即時性，換取留存率
---
↓ 順著 applies_to_personas 跳到 persona
3.
persona/sarah-busy-parent.md 
---
type: persona
id: sarah-busy-parent
pain: noise (99% 的通知不重要)
behavior: 一旦被打擾過頭，會直接全部關掉
tolerance: digest 可以接受，immediate 會崩潰
---
Agent 答覆：因為核心 persona Sarah 的痛點是 noise——預設 immediate 模式會讓她直接把所有通知關掉，等於 0 觸達率。 Digest 模式既符合她的容忍度，也保留了關鍵 alert 的觸達。決策時的明確 trade-off 是「損失即時性，換取留存率」。

這條從 page → decision → persona 的追蹤路徑就是 Vannevar Bush 1945 在 As We May Think 想做的 "associative trail"—— 紙本/微縮膠片時代沒有便宜的方式維護這張 graph（每張卡片要手工建索引，異動了還要永遠追蹤更新），LLM 時代第一次有了便宜的維護者。 這就是 4.2 cross-ref 真正在做的事。

03
— Harness · the missing governance layer

Harness 五層壓縮映射到設計工作流

Harness 原本是 LLM agent 工程的概念——管 context window、做壓縮、避免 token 爆掉。 C4 要做的映射是：把這套壓縮策略當作設計團隊的 "context 治理紀律"。 在 team scale，你 sprint 裡有太多 PRD / design review / 訪談紀錄，這就是設計版的「token 壓力」—— Harness 五層策略對映到 sprint cadence 後，就成為治理紀律。

Level Harness Op (LLM 語境) 設計工作流的對應
L1
Dedupe
移除重複訊息
 同 feature 多份重複 spec / design review notes 合併。 週會三個人都拍了同一個 Figma 截圖、各自寫了類似 comment——抓出來合併成單一 decisions/d-2026-04-xxx.md。
L2
Summarize
摘要工具輸出
 user research notes → persona / scenario page。 UR agent 跑完 8 場訪談、產出 200KB 逐字稿；不能整份塞給 Design agent——必須先摘進 personas/*.md。摘的時候保留 verbatim quote 當證據。
L3
Merge Turns
合併對話輪次
 sprint 內多次 design crit 合併成單一 decision。 sprint 中對「通知預設模式」開了 3 次討論，每次都有微調；不要保留 3 份漸進筆記——merge 成一份 decision，把 trade-off 寫清楚。
L4
Global Summary
生成全局摘要
 sprint retrospective + 下 sprint kickoff brief。 每 2 週產一份結構化摘要——這 sprint 完成什麼 decision / 留下什麼 open question / 帶到下 sprint 的 backlog。寫進 log.md，agent 跨 sprint 引用的入口。
L5
Truncate
截斷最舊記錄
 把舊 decisions 搬到 archive/（不刪除）。 一年前的 decision 還在 active 範圍裡，agent 每次 query 都吃進來——主動搬到 wiki/archive/2025-Q1/，搜尋時透過 index 仍可達到，但不會擠當前 context。Harness L5 在 agent 端記得「被截斷了什麼」；wiki 端就是 archive index。
MV
Model View
模型這輪看到的
 當 sprint 的工作 context——active personas、當前 feature 的 decisions、本 sprint AC。Agent 跑任務時只給這一份精選 context，不灌全 wiki。
PV
Persistent View
完整任務歷史
 整個 wiki + archive。agent 需要時透過 query / index 取回片段，但不預先塞進 context。這條 MV/PV 分離是 harness 治理的核心——同理也是設計團隊治理的核心。
Harness
thesis
Harness 不是 agent 工程師才需要懂的東西——它就是設計團隊在 team-scale 必須學的 context 治理紀律。 當你的 wiki 有 1000 個 page、500 個 decision、3 年累積，沒有壓縮策略 agent 跑不動，新進設計師 onboarding 會被淹沒，連 Orchestrator 自己都記不住哪個是哪個。L1-L5 對應到 sprint cadence，是讓 wiki 不腐爛的工程紀律。

05
— The meta-claim

CoT 作為通用介面 · 整個課程的論點命題化

到 C4 的這一節，整個課程的核心論點才被正面說出來： 所有節點——不同 role、不同 agent、不同 harness op、不同團隊配置——共用同一個介面：markdown + CoT 寫作。 這也是為什麼 C4 Section 04 講的兩種團隊配置能用同一套系統——因為它們都透過這個 hub 來交換工作。

所有節點被拉向同一個中心：markdown · CoT 寫作。 拿掉這個介面，圖就散了。 這就是 C1「補完 spec」的本體、C2 wiki 結構的 substrate、C3 dialectic 三節拍的書寫媒介、C4 harness governance 的表達語言。

— 為什麼這個 hub 重要：五條 compose 軸線

其他 AI/UX 工作流方案綁定特定工具或特定 platform（某個 design tool 的 AI plugin），可以 5 倍速但無法 compose。 Markdown + CoT 是唯一能同時在五個維度組合的通用介面：

i · 跨 ROLES
通用書寫介面
UR / UI / Visual / 文案都用 markdown，介面通用；不用為各 role 設計專屬工具。
ii · 跨 AGENTS
通用 context format
Design / Research / Copy / Red Team 都吃 markdown context，agent 之間可串接組合。
iii · 跨 TOOLS
viewer 可替換
Obsidian / VS Code / Cursor / Claude Code / GitHub web 都讀 markdown，工具替換成本低。
iv · 跨 TEAMS
配置可演化
Solo PD 跟 split team 用同一 substrate，可漸進演化（人多了切 role / 人少了 collapse）。
v · 跨 TIME
Git 即歷史
Git 紀錄 markdown 變更歷史；5 年後新人 onboarding 還能查回頭看「當初為什麼這樣決定」。

五層壓縮策略對應 sprint cadence、cross-role schema 統一、Model View / Persistent View 邊界清晰。Wiki 不腐爛、agent 跑得動、新人 onboarding 不被淹沒。
「我們每 2 週做 global summary 寫進 log.md；舊 decisions 主動歸 archive」
Solo PD 通常停在這層（個人尺度的終點） Split Team 跨 design team 統一 substrate（6-12 months）
L4
跨團隊 CoT 紀律 後續方向
整個 design org 用同一套 substrate。跨團隊 decision conflict 有解決路徑、新團隊 onboarding 是「指他們看 wiki」而非「重講一次」。
「新組成立第一週做的事是 fork wiki schema」
Solo PD 不適用（你還是一個人） Split Team org-level CoT council

finale
四章走完，整個論點圖完成：

C1 告訴你為什麼——86% UX 文件可結構化，spec 不會自動完成，補完 spec 是設計師的本體工作。
C2 告訴你放哪——wiki 三欄 + agents + orchestrator，markdown 是 substrate。
C3 告訴你怎麼跑——dialectic 三節拍，Red Team 必經，閉環才算一個 feature 處理完。
C4 告訴你怎麼 scale——harness governance 對應 sprint cadence、兩種團隊配置共用同一 substrate、CoT 是通用介面。

最後一句留給學員帶回公司：

設計師不是要學「用 AI」，是要學「用 CoT 把判斷寫成介面」。 介面通用，所以可以跟任何 agent 組合、任何 role 協作、任何工具搭配、任何團隊 scale。這就是 AI/UX 工作流的本體。
