Draft Brief · Prototype Ladder

From Paper to Interactive, the Rule Stays.
One Rung Was Added in the Middle.

AI didn't throw out the path from low to high fidelity. What changed: before high-fidelity tools like Claude Design and Figma, there is an unavoidable exploration phase — an unnamed middle rung now called the Annotated Prototype.

Joshua Hsiao · 2026-08 · v0.1 · Teaching brief draft for external training materials

Core Claim · What Changed Is the Thinking Container, Not the Tool
Start and end points stayed in place. What moved is the middle rung: exploration is no longer empty air, but a tangible artifact.

Leadership sees speed. Designers need to practice reorganizing what they already do — notes and comparisons while drafting screens — into conversational thinking. New tools or more expensive models won't do this for you.

§01The ladder didn't change; the middle rung did

Classic user-centered design has three steps: paper prototypes test concepts, wireframes set information architecture, and interactive prototypes run high-fidelity acceptance. AI keeps both ends and inserts a step in between.

Start and end points stay unchanged; an exploration period without design or code is inserted.

How to read this

If you plug new AI tools straight into Step 3, you skip Step 2 entirely. You don't save time; you lose the chance to converge on the concept.

§02Skip the middle rung, and screens look finished too early

Open Claude Design directly: templates look polished. But if the concept is still half-baked, you only get different layouts for the same unvetted idea. Four layouts look distinct on the surface but share the same blind spots. Trained practitioners spot this immediately; users won't.

Below is a real two-stage Annotated Prototype case — taking an interface audit tool from thesis to utility. Visual polish barely moved between the two stages; what grew significantly was conceptual convergence.

Teaching Point

Designers need judgment, not software speed: can you spot what actually changed between two prototypes? By fidelity, stage two looks more like a product. By convergence, stage one did the heavy lifting.

§03Test the water on the 1-meter board before diving from the 3-meter platform

Three heights answer three different questions. The 1-meter board is chat: check your posture and entry feel, where throwing away the whole thread costs nothing. The 3-meter board is Claude Design: template layouts turning clear concepts into screens. The high platform is Claude Code against local files: real data and live model behavior. Early divergence belongs on the 1-meter board.

Diving Order

The 3-meter board won't clarify concepts for you; it only makes clear ideas look pretty. The high platform only validates whether assumptions hold. Only the 1-meter board is built for thinking.

§04The Annotated Prototype is not a new invention, but old work in a new container

Origin of the Term

The term Annotated Prototype comes from Michael Owens (Design for Context) in his DCUX 2019 talk "Don't Document it—Prototype it!" (published 2020). All four core ideas are retained here: a hybrid of wireframes and traditional specs, annotations embedded directly in the prototype rather than linked in a separate PDF, clear non-goals (not a marketing demo, not a POC, not for user testing), and three annotation formats (sticky note / hover / off-screen).

We add one shift: moving the format from prototyping suites to HTML, so the file works as both an interactive prototype and readable documentation that agents can parse.

Designers, PMs, and engineers have always done this — back-and-forth passes with screenshots, meeting notes, and sticky annotations to get screens right. This is canvas-centric thinking: UI is separate from documentation, requiring manual effort to stitch them back together.

Before
Canvas-Centric · Detached Specs

Slides, PDFs, and meeting notes scattered everywhere, requiring manual cross-checks.

→
Target
Conversational · Embedded Context

Full context lives in a single conversation; agents need no manual stitching.

What shifts is not the annotation method, but the container: organizing fragmented notes into clean, effective conversational context.

People often compare this to Spec-Driven Development (SDD), but the direction is reversed. SDD starts from finished specs and generates code downward. Annotated Prototypes are communication-driven POCs in UX workflows — starting from unresolved concepts and converging toward consensus through the prototype itself.

ComparisonSDD · Spec-DrivenAnnotated Prototype · Communication-Driven
Starting PointWritten, fixed specificationsUnconverged concepts
DirectionSpec → CodePrototype → Consensus
ConvergenceWrite complete specs firstUse the prototype to approach consensus
WorkflowEngineering workflowUX workflow
PrerequisiteRequirements fully clearRequirements actively being negotiated
Do Not Misapply

When requirements are already locked down, SDD is faster. Annotated Prototypes solve the phase where you must start before requirements are settled. It is not an SDD replacement, but the upstream work that feeds it.

In practice, this replaces Markdown or MDX. MDX supports React and AI parsing, but non-technical stakeholders must open VS Code — which stops cross-functional communication. HTML opens cleanly in any browser, supports interactions, allows screenshots and annotations, and commits directly to GitHub.

Key Result

Prototypes and documentation are no longer two files. Online, it runs interactively; offline, the same file is the spec. You don't just save build time; you eliminate the perpetual sync drift between two documents.

This is easily confused with two other resources. The first two are searchable references; the third is a judgment on a specific screen.

Reference · Pattern Library
Answers: "What is this?"

Categorized interaction patterns to classify AI UI behaviors. It is a dictionary; it makes no judgment on a specific screen.

Judgment · Annotated Prototype
Answers: "Was it delivered?"

Applies criteria and logs evidence on a specific screen — whether what the spec claimed actually exists in the UI.

Reference · Skill Repo
Answers: "How to do this?"

Packaged methods and workflows called to execute preset steps. It is a toolbox; it does not judge specific context either.

How to Distinguish

Pattern Libraries and Skill Repos can be built in advance and reused. An Annotated Prototype only exists in front of a specific screen; changing screens requires re-evaluating criteria. That is why it cannot be stored in inventory.

§05Naming: Why not use the four existing terms

Four names already exist for parts of this. Each covers a slice, and each leads learners to misunderstand the deliverable. We exclude all four before defining the Annotated Prototype.

§06Boundaries: Three practices and three non-goals

There are no ready-made standards for this phase, so boundaries must be set clearly before it degenerates into a slide deck.

Three Practices to Keep

  • Embed annotations directly into the prototype, not in a linked PDF. The moment you link out, context scatters again.
  • Stack wireframes and specs in the same file, rather than cross-referencing two documents.
  • One file must support two modes: interactive online, readable offline.

Three Non-Goals to State

  • Not a marketing demo. It is not built to persuade; visual completion is not its goal.
  • Not for direct end-user testing. It lacks the preparation needed for formal usability studies.
  • Not the POC itself. It is the process used to produce the POC.
Why State This

If these three non-goals are omitted from the file, reviewers default to reading it as a demo. The moment it is mistaken for a demo, it must defend visual polish, and exploration ends.
